# ebpf-tui

Минимальный TUI-раннер для этого репозитория, адаптированный под модули `01..25_BPF_PROG_TYPE_*`.

Поддерживаются два режима выполнения для каждого модуля:

1) Скриптовый pipeline: **build → load/run** через `build.sh/load.sh`; проверка и отключение запускаются отдельно.
2) Native fallback: если скриптов нет, раннер сам собирает `.bpf.c`, генерирует skeleton через `bpftool`, компилирует userspace `.c` и запускает полученный loader.

## Структура проекта

```
26_EBPF-TUI/
└── ebpf-tui/                  ← корень Cargo-проекта (запуск отсюда)
    ├── Cargo.toml             ← манифест проекта (зависимости, метаданные)
    ├── Cargo.lock             ← зафиксированные версии зависимостей
    ├── README.md              ← этот файл — документация по проекту
    ├── .gitignore             ← исключения для системы контроля версий
    ├── src/
    │   ├── main.rs            ← точка входа: CLI-аргументы, инициализация терминала, цикл событий
    │   ├── ui.rs              ← отрисовка TUI-интерфейса (ratatui), состояние приложения
    │   ├── discovery.rs       ← автоматический поиск папок модулей (01..25_BPF_PROG_TYPE_*)
    │   └── runner.rs          ← запуск модулей: сборка, загрузка, выгрузка, стриминг логов
    └── target/                ← каталог сборки (генерируется cargo, не редактируется вручную)
```

### Назначение файлов

| Файл | Назначение |
|------|-----------|
| `src/main.rs` | Точка входа программы. Разбирает аргументы командной строки (clap), настраивает терминал (crossterm), запускает основной цикл обработки событий клавиатуры и сообщений от раннера. |
| `src/ui.rs` | Модуль интерфейса. Содержит структуру `App` (состояние приложения), функцию `render` (отрисовка виджетов ratatui), логику прокрутки списка модулей и окна Status. |
| `src/discovery.rs` | Модуль обнаружения. Сканирует корневой каталог репозитория и находит папки вида `01_BPF_PROG_TYPE_*` ... `25_BPF_PROG_TYPE_*`. Поддерживает вложенную структуру (fallback). |
| `src/runner.rs` | Модуль исполнения. Запускает shell-скрипты (`build.sh`, `load.sh`, `unload.sh`) или native-сборку (clang + bpftool + gcc). Стримит stdout/stderr в реальном времени в UI. |
| `Cargo.toml` | Манифест Rust-проекта: имя, версия, зависимости (ratatui, crossterm, clap, anyhow, serde_yaml и др.). |
| `Cargo.lock` | Автоматически сгенерированный файл с точными версиями всех зависимостей для воспроизводимой сборки. |

## Как это работает

- Раннер автоматически находит папки верхнего уровня вида `01_BPF_PROG_TYPE_* ... 25_BPF_PROG_TYPE_*`.
- Для каждой программы ожидаются скрипты в папке примера:
  - `build.sh` — собрать `.o` (обычно `clang -target bpf ...`)
  - `load.sh` — `bpftool prog load ...` + attach
  - `test.sh` — воспроизвести событие/трафик и проверить поведение
  - `unload.sh` — detach + очистить pinned объекты
- Во время `test.sh` раннер пишет `trace_pipe` в `trace.log`.

Если у вас нет `build.sh/load.sh/test.sh/unload.sh`, раннер будет работать через native fallback автоматически.

Если вы хотите использовать именно скрипты, можно сгенерировать их из `tutorials.md`:

```bash
python3 tools/gen_scripts_from_tutorials.py --repo-root .
```

Если вы уже генерировали скрипты ранее и хотите обновить их (например, добавить пролог генерации `vmlinux.h`), используйте `--force`:

```bash
python3 tools/gen_scripts_from_tutorials.py --repo-root . --force
```

## Структура каталогов (уровни)

```
<repo_root>/                         ← корень репозитория (здесь лежат модули)
├── 01_BPF_PROG_TYPE_CGROUP_DEVICE/
├── 02_BPF_PROG_TYPE_CGROUP_SKB/
├── ...
├── 25_BPF_PROG_TYPE_XDP/
└── 26_EBPF-TUI/                     ← папка данного модуля (TUI-раннер)
    └── ebpf-tui/                    ← Cargo-проект (запуск cargo run отсюда)
```

Таким образом, при запуске из `ebpf-tui/` раннер автоматически поднимается на **два уровня вверх** (ebpf-tui → 26_EBPF-TUI → repo_root), чтобы найти папки модулей `01..25_BPF_PROG_TYPE_*`.

## Запуск

```bash
cd 26_EBPF-TUI/ebpf-tui
cargo run --release
```

Раннер автоматически определяет корень репозитория, поднимаясь на два уровня вверх от `ebpf-tui/`.

Если автоопределение не сработало, можно явно указать корень:

```bash
cargo run --release -- --repo-root /path/to/repo_root
```

Если чтение `trace_pipe` требует пароль sudo, проще всего:

```bash
sudo -E cargo run --release
```

## Конфиг

В корне репозитория можно создать `ebpf-tui.yaml`:

```yaml
trace_cmd: "sudo cat /sys/kernel/tracing/trace_pipe"
artifacts_dir: "artifacts"
```

## Логи

После запуска шагов логи пишутся в:

`artifacts/<program>/`

Файлы: `build.log`, `load.log`, `test.log`, `unload.log`, `trace.log`, `native_run.log`.

Отдельно общий поток окна `Status` сохраняется в:

`artifacts/status_window.log`

Для ручной проверки модулей по отдельности дополнительно пишутся:

- `manual_build.log`
- `manual_load.log`
- `manual_test.log`
- `manual_unload.log`
- `manual_trace.log` (живой trace для проверки в другом окне)
- `manual_trace_start.log`, `manual_trace_stop.log`

Также для каждого прогона формируются:

- `status.log` — компактная статус-сводка в текстовом виде.
- `run_report.md` — структурированный отчёт по модулю и доступным логам.

## Интерфейс

Приложение имеет две вкладки, переключение по `Tab`:

### Вкладка Runner (управление модулями)

- Левая панель `Programs` — список всех обнаруженных модулей с прокруткой (↑/↓).
- Правая верхняя панель `Status` — лог событий раннера в реальном времени с прокруткой (`[`/`]`).
  - Лог автоматически очищается при каждом новом запуске модуля.
  - При поступлении новых строк окно автоматически прокручивается вниз.
  - При ручной прокрутке автоскролл отключается до нажатия `g`.
- Правая нижняя панель `Module card` — микро-описание выбранного модуля, прогресс, статус attached/trace.

### Вкладка Statistics (сбор и отображение статистики)

- **График активности (Sparkline)** — визуализация количества событий в секунду за последние 60 секунд. Позволяет оценить интенсивность работы модулей в реальном времени.
- **Гистограмма событий по типам (BarChart)** — столбчатая диаграмма с распределением событий: build, load, run, stop, fail, trace. Показывает общую картину использования системы.
- **Таблица событий (Table)** — табличное представление всех событий с колонками: время, модуль, тип, сообщение. Поддерживает прокрутку (↑/↓). Хранит до 5000 записей.

Данные собираются в реальном времени из всех операций с модулями и сохраняются в архив (`artifacts/status_window.log`).

### Горячие клавиши

| Клавиша | Действие |
|---------|----------|
| `Tab` | Переключение между вкладками Runner / Statistics |
| `↑` / `↓` | Runner: выбор модуля; Statistics: прокрутка таблицы |
| `l` | Загрузить модуль (build + load → статус `run`) |
| `s` | Остановить/открепить модуль |
| `[` | Прокрутка окна Status вверх (Runner) / таблицы (Statistics) |
| `]` | Прокрутка окна Status вниз (Runner) / таблицы (Statistics) |
| `g` | Вернуть автоскролл Status (Runner) |
| `PgUp` / `PgDn` | Прокрутка (если терминал пропускает) |
| `q` | Выход |

### Ручная проверка заказчиком

Рекомендуемый порядок для каждого модуля:

1. `l` (build + attach к ядру, переход в `run`)
2. `s` (остановить/открепить модуль)
